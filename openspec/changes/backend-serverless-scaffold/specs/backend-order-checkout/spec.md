## Purpose

處理學生報名下單、金流商整合下單參數，以及付款狀態機的伺服器端保證，確保付款狀態僅由驗證過的金流商通知驅動。

## ADDED Requirements

### Requirement: 訂單付款方式必須是課程開放的選項
系統 SHALL 依課程設定的付款方式驗證報名請求；若請求的付款方式不在該課程開放清單中，SHALL 拒絕建立訂單。

#### Scenario: 選擇課程未開放的付款方式被拒絕
- **WHEN** 學生報名一個僅開放 ATM 的課程，但請求中選擇信用卡付款
- **THEN** 系統拒絕建立訂單並回傳付款方式不受支援的錯誤

### Requirement: 依課程付款方式設定決定金流商下單參數
系統 SHALL 依課程設定的付款方式決定呼叫金流商（綠界/藍新）下單時的 `ChoosePayment` 參數（ATM／Credit／ALL），並在訂單記錄中保存本次下單使用的金流商與參數，供後續對帳查核。

#### Scenario: 兩種付款方式皆開放時下單參數為 ALL
- **WHEN** 學生報名一個同時開放 ATM 與信用卡的課程
- **THEN** 系統呼叫金流商下單時帶入 `ChoosePayment=ALL`

### Requirement: 付款狀態僅由驗證過的背景通知更新且處理具冪等性
系統 SHALL 限制訂單付款狀態只能透過驗證過的金流商背景通知更新，SHALL NOT 提供任何允許用戶端直接宣告付款完成的 API。每筆背景通知 SHALL 以金流商提供的唯一交易識別碼判斷是否已處理過；已處理過的重複通知 SHALL 被安全忽略，不得重複更新狀態或重複觸發下游通知。

#### Scenario: 重複收到同一筆背景通知只處理一次
- **WHEN** 系統收到同一筆金流商背景通知兩次（相同交易識別碼）
- **THEN** 訂單狀態僅被更新一次，且下游的通知派送只被觸發一次

#### Scenario: 用戶端無法自行宣告付款完成
- **WHEN** 用戶端嘗試呼叫任何 API 直接將訂單標記為已付款
- **THEN** 系統不存在此類端點，或明確拒絕該操作

### Requirement: ATM 逾期與退款方式差異
系統 SHALL 記錄 ATM 訂單的繳費期限，超過期限仍未付款的訂單 SHALL 轉為逾期狀態。退款處理時，信用卡訂單 SHALL 透過金流商 API 自動退款；ATM 訂單 SHALL 標記為「待人工轉帳」，需管理者人工執行轉帳並回填憑證後才能將該筆退款標記為完成。

#### Scenario: ATM 訂單核准退款後標記待人工轉帳
- **WHEN** 一筆 ATM 付款的訂單退款申請被核准
- **THEN** 系統將該筆退款標記為「待人工轉帳」，不嘗試呼叫任何自動退款 API
